# 抖音网页版手势控制器 · 产品设计文档 v0.3

> 状态：演示版已实现并验证（`demo/pose.html`）
> 上一版：v0.2（动态滑动方案，`docs/PRD-v0.2.md`）
> 文档定位：当前生效规格。v0.1 / v0.2 保留为历史存档。

---

## 0. 本版变更总览

| 项 | v0.2 | v0.3 | 原因 |
|---|---|---|---|
| 手势类型 | 动态滑动手势 | **静态数字手势** | 动态手势命中率实测过低 |
| 判据核心 | 五指伸直 + 并拢 + 掌面 + 纵向位移 | **指型匹配 + 几何有效性 + 保持时长** | 位移类判据受速度、出框影响极大 |
| 方向映射 | 上滑 → 下一个，下滑 → 上一个 | **比 1 → 下一个，比 2 → 上一个** | 用户指定 |
| 误触防护 | 冷却 1000ms | 保持 300ms + **触发后锁定** + 冷却 1000ms | 收手回弹会凑出反向位移 |
| 无效判定 | 无 | **出框保护 + 距离保护** | 手被画面裁断会把掌宽算小，导致归一化数值虚高 |

## 1. 产品定义

在 Edge 浏览器的抖音网页版上，用摄像头识别手部姿态，以「比数字」的方式切换视频，替代鼠标滚轮与键盘方向键。

**一句话**：手心朝镜头比个数字，视频就跟着走。

---

## 2. 为什么从滑动改成比数字

v0.2 的动态滑动方案在真机上暴露了两个硬问题：

1. **命中率低**。滑动要求「五指伸直 + 五指并拢 + 掌面朝前 + 纵向位移达标」四项在同一时间窗内同时成立。人手在挥动时手腕必然旋转，中途会短暂侧对镜头，判据当场失效。
2. **误触难消**。下滑触发后，手自然收回原位，这段回弹本身就是一段向上位移，冷却一过就触发反向动作。

静态手势把这两个问题从根上绕开了：

- 不需要速度 → 不存在「挥太快抓不到」；
- 不需要位移 → 不存在「回弹凑出反向位移」；
- 指型是离散量（伸 1 根 / 伸 2 根）→ 判据边界清楚，不像连续位移要靠阈值卡。

代价是**单次操作慢一点**（要停 0.3 秒），这是明知的产品取舍。

---

## 3. 手势词典

| 手势 | 动作描述 | 结果 | 判定要点 |
|---|---|---|---|
| **比 1** | 手背朝镜头，只伸食指，其余三指收拢 | 下一个视频 | 食指伸直、中指/无名指/小指弯曲 |
| **比 2** | 手背朝镜头，食指与中指伸出，其余两指收拢 | 上一个视频 | 食指+中指伸直，无名指/小指弯曲 |

**为什么方向这样定**：比 1 是「一根手指往上指」，对应向下滑动的语义（下一个）；比 2 反之。这是用户习惯，不是技术约束，改一行映射即可对调。

**明确不接受的手型**（一律判为无效，不触发）：

| 手型 | 结果 | 说明 |
|---|---|---|
| 握拳 | 无效 | 用于「解锁」，见 §5 |
| 五指张开 | 无效 | 三条以上手指伸直不匹配任何模板 |
| 三根手指（1+中+无名） | 无效 | 避免与比 2 混淆 |

## 4. 判定判据

四条同时满足才触发，缺一不可。

### C1 单手可见

MediaPipe Hands 检出至少一只手，且关键点齐全（21 点）。

### C2 指型匹配（核心）

对食指、中指、无名指、小指分别判断「伸直」：

```
伸直程度 = 指尖到腕的距离 ÷ 该指指根(PIP)到腕的距离
伸直 ⟺ 比值 > 1.15
```

用比值而不是关节夹角，原因有两条：

- **与尺度无关**：手离镜头远近不影响比值；
- **与旋转无关**：手转半侧时比值几乎不变，夹角会剧烈变化。

实测参考值：伸直 ≈ 1.3–1.5，弯曲 ≈ 0.6–0.9，阈值 1.15 落中间，两侧都有余量。

### C3 几何有效性

| 检查 | 阈值 | 不通过时 |
|---|---|---|
| 出框 | 任一关键点落在画面边缘 1.5% 内 | 不触发，提示「手太靠边 · 往中间挪」 |
| 距离 | 掌宽 < 22 px（640×480 下） | 不触发，提示「离镜头近一点」 |

这一条是 v0.3 新增，起因见 §7 的一次实测。

### C4 保持时长

同一指型连续保持 ≥ 300ms。

- 指型一变即重新计时，避免「路过比 1 的位置」被计入；
- 300ms 是灵敏度按钮：调到 200ms 更快但更易误触，调到 500ms 更稳但更迟钝。

## 5. 状态机

```
         ┌──────────────┐
         │   待命 armed  │◄──────────────┐
         └──────┬───────┘               │
                │ 识别到指型 1 或 2       │ 收成非 1/2 手型
                │ 且 C3 通过            │ 或换成另一个数字
                ▼                       │ 或手离开画面
         ┌──────────────┐               │
         │  计时 holding │               │
         │  < 300ms     │               │
         └──────┬───────┘               │
                │ 保持满 300ms          │
                ▼                       │
         ┌──────────────┐               │
         │  触发 firing  │               │
         └──────┬───────┘               │
                │ 切视频 + 进入锁定      │
                ▼                       │
         ┌──────────────┐               │
         │  锁定 locked  │───────────────┘
         └──────────────┘
```

**锁定是防误触的关键**：触发后同一姿势继续举着不会重复触发，必须先「放下」或「换一个数字」。这条规则直接消灭了 v0.2 的回弹误触。

## 6. 参数表

| 参数 | 默认值 | 可调范围 | 作用 |
|---|---|---|---|
| 保持时长 hold | 300 ms | 120–800 ms | 灵敏度总开关 |
| 冷却 cool | 1000 ms | 400–2500 ms | 两次触发的最小间隔 |
| 手指伸直阈值 curl | 1.15 | 1.02–1.40 | 越小越容易判为伸直 |
| 出框边距 | 1.5% | 固定 | 画面边缘安全边 |
| 最小掌宽 | 22 px | 固定 | 距离下限 |
| 模型复杂度 | 0（lite） | 固定 | 速度优先 |

调参优先级：**先调保持时长，再调伸直阈值，最后才动冷却**。冷却只影响连续操作间隔，不影响单次成败。

## 7. 一次实测暴露的问题（已修）

从真机录屏的调试面板中读到一组异常数据：

```
纵向  +2.11 / 0.75        阈值 0.75，实测 2.11
并拢  0.55 / 0.55
掌面  0.86 / 0.55
```

**+2.11 掌宽在物理上不可能**（手在一个时间窗内移动不了两个多掌宽）。追溯原因是手贴在画面最右侧，指尖被裁掉，MediaPipe 只能按可见部分推算，导致掌宽被算小；而位移是用掌宽归一化的，**分母一小，位移虚高**。

结论：所有「除以掌宽」的判据，在关键点出框时都会失真。这直接催生了 C3 的几何有效性检查。

同时修掉的两个工程问题：

| 问题 | 现象 | 修法 |
|---|---|---|
| 帧率虚报 | 摄像头 30fps，界面显示 91fps | 送帧循环按屏幕刷新率跑，同一帧被送两遍；改为按帧回调计数，且只送新帧 |
| 保持值失真 | 触发后显示「保持 6004 / 300ms」 | 锁定后计时器继续累加；改为显示「已触发」 |

## 8. 界面规格

| 元素 | 位置 | 规格 |
|---|---|---|
| 摄像头预览 | 右下角 | 168 px 宽，点击标题放大至 360 px |
| 安全区虚线框 | 预览内 10% 内缩 | 提示手应放置的范围 |
| 手部骨架 | 预览内叠加 | 青色 = 正常；**琥珀色 = 出框，判定不可靠** |
| 保持进度条 | 预览底部 3 px | 0→100% 对应 0→300ms |
| 四条件面板 | 预览下方 | C1 单手可见 / C2 比出 1/2 / C3 可触发 / C4 保持达标 |
| 实时数值 | 四条件下方 | 指型 / 朝面 / 保持 / 锁定 |
| 调试面板 | 左下角，可折叠 | 帧率、延迟、触发次数 + 三个滑杆 + 一键放宽 |
| 开关 | 右下角浮动按钮 | 快捷键 `Alt+Shift+G` |

**状态灯四态**：灰 = 关闭，绿 = 待命，青 = 检测到手，蓝闪 = 已触发。

## 9. 验收指标

| 指标 | 目标 | 测法 |
|---|---|---|
| 单次命中率 | **≥ 95%** | 连续比 1 共 40 次，记录成功次数 |
| 静止误触发 | **≤ 1 次 / 10 分钟** | 手放桌上不动，看完一条 10 分钟视频计数 |
| 端到端延迟 | **≤ 400 ms** | 保持 300ms + 处理约 50ms；秒表或慢动作录屏 |
| 识别帧率 | **≥ 15 fps** | 预览窗实时显示 |
| 手势切换误触 | **≤ 1 次 / 10 次切换** | 比 1 → 比 2 → 比 1 来回切 10 轮，记录误触 |
| 内存增量 | **< 300 MB** | 任务管理器看 Edge 进程组 |

延迟目标从 v0.2 的 300ms 放宽到 400ms，是静态手势「必须停一下」的必然代价，属于设计选择而非退步。

### 10.2 手动清单（需真人）

自动化测不了「你的手能不能被识别」，这部分只能人测：

1. 距离 40–60cm，手在虚线框内举 1，看「指型」是否显示「比 1」。
2. 保持 0.3 秒后应切到下一个视频，且进度条在切换瞬间走满。
3. 切换后**继续举着不动**，不应再触发（锁定生效）。
4. 放下手，再举 2，应回到上一个。
5. 把手移到画面最右边，骨架应变琥珀色、状态栏提示「手太靠边」，且不触发。
6. 手往后退到画面里很小，「朝面」下方提示「离镜头近一点」，不触发。

## 11. 风险与对策

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | 抖音网页版滚动容器无法被程序化驱动 | 中 | **致命**（整个方案不成立） | 扩展注入前必须先做 DOM 探测，探测不通过就转「模拟键盘方向键」或「点击切换按钮」 |
| 2 | 逆光或暗光导致关键点抖动 | 高 | 命中率下降 | 界面提示补光；实测暗光下摄像头自动降帧到 15fps，仍可识别 |
| 3 | 用户自然手型不是标准「1/2」 | 中 | 个别用户命中率低 | 伸直阈值可调；后续可加「录制我的 1/2」标定流程 |
| 4 | 手与脸重叠，z 估计跳变 | 中 | 朝面数值不稳 | 朝面已不参与触发，只作提示；必要时提示手前伸 |
| 5 | 笔记本电脑摄像头位置偏低，视角仰拍 | 低 | 手型变形 | 提示抬高笔记本或后仰屏幕 |
| 6 | 扩展内摄像头权限（iframe allow 策略） | 中 | 无法取流 | 备用 offscreen document 方案 |

## 13. 已明确不做

| 不做 | 理由 |
|---|---|
| 点赞 / 收藏 / 关注 / 评论手势 | 误触代价高，可能触发风控；滑动误判最多多刷一条 |
| 音量、进度手势 | 原生方向键和空格更快更准 |
| 双手识别 | 帧率减半，本场景无收益 |
| 惯性滚动、手势动画 | 拉长延迟，制造「手与画面不同步」的错觉 |
| 掌面/手背严格区分 | 区分靠指型已足够；朝向判定受左右手与镜像影响，判错即全错 |

## 附录 A：与 v0.2 的判据对照

| 维度 | v0.2（滑动） | v0.3（比数字） |
|---|---|---|
| 输入特征 | 手掌质心位移 + 手指几何 | 手指伸直模式 |
| 时间维度 | 时间窗 500ms 内的位移量 | 同一姿势的持续时间 |
| 稳定性来源 | 动作要「标准」 | 姿势要「保持」 |
| 失败模式 | 挥太快 / 手转侧 / 出框 | 手型不标准 / 手太小 / 出框 |
| 抗误触 | 冷却 | 冷却 + 锁定（更强） |
| 用户学习成本 | 低（像滑屏） | 中（要记住 1 和 2 的方向） |
