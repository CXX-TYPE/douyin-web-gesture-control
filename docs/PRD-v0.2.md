## 0. 本版改了什么

v0.1 的手势描述是推测的（「手掌上移 / 下移」），本版依据一段 5.93 秒的实拍视频重新校准：

| 项 | v0.1 | v0.2 |
|---|---|---|
| 手势 1 | 手掌上移 | **五指平行上滑** → 下一个视频 |
| 手势 2 | 手掌下移 | **五指平行下滑** → 上一个视频 |
| 判据 | 只看手掌中心位移 | 位移 + 五指姿态 + 掌面朝向 + 伴随旋转 |
| 时间窗 | 400ms | 800ms（实测动作时长约 900ms） |
| 冷却时间 | 800ms | **1000ms**（1 秒，比时间窗长 200ms） |
| 位移阈值 | 1.2 掌宽 | 1.0 掌宽（实测约 0.3 画面高） |

其余章节（目标、范围、交互、验收、里程碑、风险）保持 v0.1 不变。

## 1. 一句话定义

在 Edge 里用摄像头识别**五指并拢伸平的手掌**做垂直挥动，上滑切下一个视频、下滑切上一个视频。

---

## 2. 视频分析结论

**素材**：5.93s，720×1280，30fps，HEVC。手持竖屏拍摄，架在笔记本前方，画面包含笔记本屏幕与键盘。

**分析方法**：按 10fps 抽帧共 59 帧，逐帧观察手部姿态，并用肤色质心估算纵向轨迹，两者交叉校对。

**动作时间线**：

| 时间 | 手部状态 | 位置 |
|---|---|---|
| 0.0–0.3s | 五指并拢伸直，掌面朝下，手呈水平「手刀」状，指尖朝左 | 屏幕中部 |
| 0.3–1.2s | 整体向上扫动，手腕自然内旋，结束时指尖朝上 | 中部 → 上部 |
| 1.2–3.4s | 手回落并离开画面 | —— |
| 3.5–4.5s | 手重新抬至屏幕区域 | 下部 → 中部 |
| 4.5–5.9s | 向下扫出画面，指尖由朝上转为朝左下 | 中部 → 下缘 |

**三条对设计有直接影响的观察**：

1. **动作伴随旋转**。起点手是横的（指尖朝左、掌心朝下），终点手接近竖的（指尖朝上）。如果只判 `Δy` 而不看姿态变化，容易把「抬手」误判成「上滑」。→ 判据必须包含掌面朝向。
2. **五指是并拢的**，不是张开的。这反而是好事：并拢姿态的指尖间距小、外轮廓稳定，比张开手掌更容易做形状校验。
3. **动作时长约 900ms，位移约 0.3 个画面高度**。这比 v0.1 假设的「400ms 内完成」慢一倍，时间窗必须放宽，否则正常速度的手势会被判失败。

## 3. 手势词典

| # | 名称 | 定义 | 触发 | 视频依据 |
|---|---|---|---|---|
| G1 | **五指平行上滑** | 五指并拢伸直、掌面朝摄像头，整体向上移动 | 下一个视频 | 0.3–1.2s |
| G2 | **五指平行下滑** | 同上，方向向下 | 上一个视频 | 4.5–5.9s |
| G3 | （预留）握拳保持 | 五指收拢保持 N 帧 | 暂停 / 播放 | 未在视频中出现 |

### 3.1 判定条件（四个必须同时满足）

| # | 条件 | 阈值 | 作用 |
|---|---|---|---|
| C1 | 五指伸直 | 每根手指的 MCP–PIP–DIP 夹角 > 160° | 排除握拳、半握、比耶 |
| C2 | 五指并拢 | 相邻指尖间距 < 0.25 × 掌宽 | 排除张开手掌、挥手 |
| C3 | 掌面朝向摄像头 | 掌心法向量与相机光轴夹角 < 45° | 排除手背朝镜头、侧手 |
| C4 | 纵向位移达标 | 手掌中心纵向位移 > 1.0 × 掌宽，且横向位移 < 0.5 × 纵向位移 | 排除斜挥、横向划过 |

**方向判定**：C4 的位移符号决定是 G1（向上）还是 G2（向下）。

**掌宽定义**：食指根（landmark 5）到小指根（landmark 17）的距离，用作归一化基准，抗手与摄像头距离变化。

### 3.2 时序参数

| 参数 | 值 | 依据 |
|---|---|---|
| 时间窗 | 800ms | 实测动作时长约 900ms，留 100ms 容差 |
| 冷却时间 | 1000ms | 比时间窗长 200ms，保证一次完整动作收尾后仍有缓冲，不会被切成两次 |
| 起始静止要求 | 位移开始前，手需在 200ms 内位移 < 0.2 掌宽 | 排除「已经在动」的连续挥动被切成两次 |

> 三个参数联合决定「顺手」与「闹心」的平衡点。M3 阶段用误触发指标（≤1 次/10 分钟）反推这三个值；若要放宽时间窗，冷却时间同步顺延，两者始终保持 200ms 的差值（当前 800 / 1000）。

## 4. 目标与非目标

### 4.1 目标

| 优先级 | 目标 |
|---|---|
| P0 | 手不碰键鼠，能连续切换视频 |
| P0 | 端到端延迟 ≤ 300ms（手势结束 → 画面切换） |
| P0 | 静止误触发 ≤ 1 次 / 10 分钟 |
| P1 | 随手开关，不用时摄像头真正释放 |
| P2 | 识别结果可视化，便于调参 |

### 4.2 非目标

| 不做的 | 原因 |
|---|---|
| 点赞 / 收藏 / 关注 / 评论 | 误触代价高，属社交动作，有账号风险 |
| 音量 / 进度手势 | 原生键鼠更快更准，负收益 |
| 移动端 | 手机自带滑动，无需求 |
| 通用网页手势控制 | 首版只服务 douyin.com |
| 账号体系 / 云同步 | 单人自用 |

## 5. 用户与场景

**用户**：本人，单人自用，不分发上架。

**典型场景**：晚上在笔记本前，手自然放在桌面或腿上，视线在屏幕，用手掌上下挥动切视频。

**不适用场景**（不作为设计目标）：

| 场景 | 失效原因 |
|---|---|
| 强背光 / 逆光 | 手部轮廓分割失败，C3 掌面朝向判定失准 |
| 多人同框 | 检测到多手时判定不确定 |
| 手被桌面、被子遮挡 | 关键点置信度低于阈值 |
| 手离摄像头 < 20cm | 手部超出画面，landmark 缺失 |

## 6. MVP 范围

| # | 功能 | 优先级 | 验收标准 |
|---|---|---|---|
| 1 | 五指平行上滑 → 下一个视频 | P0 | 连续 50 次成功 ≥ 45 次 |
| 2 | 五指平行下滑 → 上一个视频 | P0 | 连续 50 次成功 ≥ 45 次 |
| 3 | 悬浮状态灯（关闭/待命/检测到/触发） | P0 | 四态肉眼可区分 |
| 4 | 快捷键开关 `Alt+Shift+G` | P0 | 关闭后摄像头指示灯熄灭 |
| 5 | 手部预览小窗（可折叠） | P1 | 折叠后不遮挡视频 |
| 6 | debug 页（骨架 + FPS + 四条件实时命中状态） | P1 | 能看出 C1–C4 哪一条没过 |

> 第 6 项相比 v0.1 增强了：因为判据从 1 条变成 4 条，调参时必须能看到**是哪条条件卡住了**，否则只能盲目试。

**本版不做**：第三种手势、设置面板与持久化、惯性滚动、手势动画与音效。

## 7. 交互设计

### 7.1 状态灯

| 状态 | 颜色 | 含义 |
|---|---|---|
| 关闭 | 灰 | 未启用，摄像头已释放 |
| 待命 | 绿（呼吸） | 已启用，未检测到手 |
| 检测中 | 青 | 手已识别，C1–C3 部分满足 |
| 触发 | 蓝（闪一下） | 刚发出切换指令 |

### 7.2 预览小窗

- 位置：右下角，距边 16px
- 尺寸：展开 160×120，折叠 48×48
- 内容：镜像画面 + 骨架线，命中全部条件时骨架变蓝
- 交互：点击折叠/展开，可拖动

### 7.3 首次使用引导

1. 点扩展图标 → 弹出授权
2. 允许摄像头 → 预览窗出现，提示「五指并拢，向上挥一下」
3. 第一次成功触发 → 提示消失

## 8. 技术方案概要

| 环节 | 选型 | 关键参数 | 理由 |
|---|---|---|---|
| 扩展形态 | MV3 | service worker + content script | Edge / Chrome 通用 |
| 手部识别 | MediaPipe Tasks `HandLandmarker` | 21 点/手，最多 2 手，WASM + GPU delegate | 帧率与精度平衡最好，模型约 7.8MB |
| 摄像头承载 | 扩展页 iframe + `allow="camera"` | 扩展源授权 | 避免「douyin.com 请求摄像头」的怪异提示 |
| 通信 | `postMessage` | 单向事件流 | 简单 |
| 页面注入 | content script | `matches: *://*.douyin.com/*` | 标准做法 |
| 滚动驱动 | **待 M1 探测确定** | 见第 11 节风险 1 | 三选一，必须实测 |

### 8.1 数据流

```
摄像头帧 → HandLandmarker → 21 关键点
    → 姿态判定 C1/C2/C3（每帧）
    → 位移追踪 C4（跨帧，滑动窗口 800ms）
    → 手势标签 G1/G2 → postMessage
    → content script → 滚动指令 → 视频切换
```

**分层原因**：C1–C3 是逐帧判定（只看当前手势形状），C4 是时序判定（要看最近 800ms 的轨迹）。分开实现，前者是纯函数，后者是状态机，都能单测。

### 8.2 模块划分

| 模块 | 职责 | 可测试性 |
|---|---|---|
| `landmark-pose.js` | 关键点 → C1/C2/C3 布尔值 | 纯函数，可单测 |
| `trajectory.js` | 位移序列 → C4 + 方向 | 纯状态机，喂坐标序列可测 |
| `recognizer.js` | 组合上述两者 → 手势标签 | 纯函数，可单测 |
| `injector.js` | 手势事件 → DOM 操作 | 需真实 DOM，集成验证 |
| `debug.html` | 可视化与调参 | 人工验证 |

## 9. 验收指标

| 指标 | 目标 | 测量方法 |
|---|---|---|
| 端到端延迟 | ≤ 300ms | 240fps 慢动作录屏，数帧 |
| 单次识别率 | ≥ 90% | 连续 50 次，人工计数 |
| 静止误触发 | ≤ 1 次 / 10 分钟 | 手放桌上不动，看 10 分钟视频 |
| 抬手误触发 | ≤ 1 次 / 20 次 | 只抬手不挥动，做 20 次，看是否误判为 G1 |
| 识别帧率 | ≥ 25 fps | debug 页实时显示 |
| 内存增量 | < 300MB | 任务管理器 |

> 第 4 项是本版新增。视频分析显示动作伴随旋转，因此「单纯抬手」是最可能被误判成 G1 的动作，必须单独计量。

## 11. 风险与对策

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | 抖音滚动容器无法程序化驱动 | 中 | **致命** | M1 先探测，三方案并行：容器 `scrollBy` / 派发方向键 / 点切页按钮 |
| 2 | Edge 对 iframe `allow="camera"` 限制更严 | 中 | 高 | 备选：offscreen document 承载摄像头 |
| 3 | 集显帧率不足 25fps | 中 | 中 | 输入降到 320×240；启用 GPU delegate；检测频率降到 15fps |
| 4 | 抬手动作被误判为上滑 | **高** | 高 | 严格 C1（五指必须伸直）+ 起始静止要求；按第 9 节第 4 项专门验证 |
| 5 | 抖音前端改版导致选择器失效 | 低 | 中 | 选择器集中到一个常量文件 |

第 4 条是本版升级为「高概率」的风险，依据来自视频：真实使用中抬手、挠头、端杯子都会经过相似轨迹。

## 附录 A：关键决策记录

| 决策 | 选了 | 放弃了 | 理由 |
|---|---|---|---|
| 判据维度 | 姿态 + 轨迹双重判定 | 只看位移 | 视频显示动作含旋转，只看位移无法区分「挥手」和「抬手」 |
| 手势数量 | 2 个 | 4 个以上 | 调试成本随数量非线性上升 |
| 触发动作 | 视频切换 | 点赞、评论 | 误触代价不对称，只有滑动「错了也无所谓」 |
| 位移归一化 | 掌宽 | 绝对像素 | 抗距离变化，免重调参 |
| 时间窗 | 800ms | 400ms | 实拍动作 900ms，400ms 会让正常手势判失败 |
| 事件合成 | 操作 DOM | 合成键盘事件 | `isTrusted=false` 可能被忽略 |
